# Validation

v1 validates requests against the contract's Standard Schema slots: query and body (a headers schema is not enforced yet). The schema-agnostic primitive lives in `@laratype/contract`. Running it in the request pipeline belongs to `@laratype/http` (H3), and Laravel-style request classes belong to `@laratype/validation` (H10). `@laratype/validation` on master is still the 0.5 package.

## Standard Schema adapter

### Status
merged @ 883a8e2 (C3 [#91](https://github.com/Laratypes/Laratype/issues/91)).

### Public API
Specified in full in [contract.md › Validation adapter](./contract.md#validation-adapter). It is not repeated here, so the two copies can't drift. In summary: `validate(schema, value)` and `validateSync(schema, value)` return `ValidationResult<O>`, `toErrorBag(issues)` builds an `ErrorBag`, and the `StandardIssue` type is exported.

### Invariants
- Invalid input resolves to `{ ok: false, errors, issues }` and never rejects.
- `ErrorBag` maps dot paths to messages. It has a null prototype, and issues without a path go under `""`.
- The `errors` bag has exactly the shape of the 422 body, `ValidationErrorBody.errors` ([contract.md › Error catalog](./contract.md#error-catalog)).

### Diagnostics
See [contract.md › Validation adapter](./contract.md#validation-adapter).

### Example
[`examples/contract/validate.ts`](./examples/contract/validate.ts)

### Non-goals
- No messages, i18n, `authorize()` or DB rules at this layer.

### Open questions
- None recorded.

## Pipeline validation and 422

### Status
proposed: PR [#345](https://github.com/Laratypes/Laratype/pull/345) @ e54cb4d (H3 [#106](https://github.com/Laratypes/Laratype/issues/106), H26 [#287](https://github.com/Laratypes/Laratype/issues/287), H43 [#340](https://github.com/Laratypes/Laratype/issues/340)). B30 [#410](https://github.com/Laratypes/Laratype/issues/410) re-read the body-cache shapes, the form conversion and the form classifier, and refused a multi-valued `Content-Type` and a form media type name outside the leading media type before them, at [4109aef3](https://github.com/Laratypes/Laratype/commit/4109aef3). H31 [#308](https://github.com/Laratypes/Laratype/issues/308) follows up on the 422 messages, the JSON media type and the one query parse at [9b7c5a4b](https://github.com/Laratypes/Laratype/commit/9b7c5a4b) (PR [#429](https://github.com/Laratypes/Laratype/pull/429)). The spec for the pipeline as a whole is in [http.md › Request pipeline](./http.md#request-pipeline).

### Public API
No new export: `RequestKernel.handle` runs it for every `Route.api` contract route, and the handler gets the ctx (an [ad-hoc route](./http.md#ad-hoc-routes) has no contract: its body is parsed as below, a malformed one is the same 400, but nothing is validated and its handler gets the 0.5 request) typed by `Ctx<E>` ([http.md › Controller typing](./http.md#controller-typing-ctx-and-controllerof)). Code: [`request/input.ts` @ 67dd9255](https://github.com/Laratypes/Laratype/blob/9b7c5a4bff4aac683c4546c55b602b3696e86cd5/packages/http/src/request/input.ts), [`request/Request.ts` @ dce2f385](https://github.com/Laratypes/Laratype/blob/dce2f385f3dbf9416e9f1ca6b25fa0d12451461e/packages/http/src/request/Request.ts) (`RequestKernel`), [`routing/api/proof.ts` @ dce2f385](https://github.com/Laratypes/Laratype/blob/dce2f385f3dbf9416e9f1ca6b25fa0d12451461e/packages/http/src/routing/api/proof.ts).

```ts
// @laratype/http (RequestKernel is the default export of request/Request.ts)
class RequestKernel { static handle(routeOption: RouteParams): (ctx: Context) => Promise<void> }   // throws a TypeError for a contract route with a request class
export type BaseCtx<E extends AnyEndpoint, P = PathParams<E path>> = {
  readonly endpoint: E;
  params: P;                        // raw path params (strings)
  query: InferOut<E query schema>;  // undefined without one
  body: InferOut<E body schema>;    // undefined without one
};
export type Ctx<E extends AnyEndpoint, Requires extends object = {}>;   // BaseCtx<E> merged with Requires, params one level deep
```

### Invariants
- **Body by media type:** `application/json` and `application/*+json`, in any case, and only the leading media type decides (H31 [#308](https://github.com/Laratypes/Laratype/issues/308)): the parameters are ignored (`; charset=utf-8`, an empty parameter list after a trailing `;`, a `_` in a parameter name, a quoted `;` in a value), as is the OWS RFC 9110 §8.3.1 allows before the `;` (`application/json ; charset=utf-8`); the subtype may hold `_` and `+` (`application/vnd.my_app+json`, `application/vnd.a+b+json`, RFC 6838). That is broader than Hono's `validator('json')` media type on purpose: the pipeline reads the body itself, so a header that regex rejects (`application/json;`) is JSON here, not `{}`. Anything else is read as Hono's `parseBody({ dot: true })` reads it: `multipart/form-data` and `x-www-form-urlencoded` fields (`user.age` becomes `{ user: { age } }`), `{}` for other types. The `formMediaType` helper describes both `parseBody()` classifiers in the peer range and the 0.5 cap's rule: 4.8.0–4.12.27 matches the value `headers.get("Content-Type")` returns with a case-sensitive `startsWith` (`Headers` strips leading/trailing HTTP whitespace, not U+00A0), 4.12.28+ splits at `;`, trims, lowercases and compares exactly to `multipart/form-data` / `application/x-www-form-urlencoded`, and the 0.5 cap's lowercased `startsWith` also returns a form for a suffixed spelling the exact rules miss. A `Content-Type` naming more than one media type (a comma outside a quoted-string, RFC 9110 §5.6.4, so `boundary="a,b"` is one value and a quoted `\"` is an escaped quote; an unterminated quoted-string quotes nothing, so its comma is a separator too) is never classified or capped: it is the 400 `{ message: "Invalid Content-Type header: more than one media type." }` at the start of the read, before the default cap, because the header is a singleton field (RFC 9110 §8.3) and the platform's MIME extraction takes the last value. A form media type name outside the leading media type is refused the same way, as `{ message: "Invalid Content-Type header: a form media type name outside the leading media type." }`, before this classification: Bun's form parser searches the whole header, so only a leading type that is exactly one of the two form names can be parsed and capped. Through `readBody` the three arms decide nothing for a suffixed or embedded form name in the leading type — that header is the form-name 400 before the helper — so the 0.5 arm does not restore a pipeline parse. A header with a leading type exactly one of the two form names is read as a form (fail closed), lowercases the media type for its own parser (the parameters, a multipart boundary included, keep their case), and a spelling none of the arms reads is `{}` when it reaches the helper (it has no form name); the default cap uses the same three-arm rule. A form key in which `__proto__` is a segment at the start or after a dot **and followed by another segment** (`__proto__.x`, `a.__proto__.x`) is dropped, as Hono 4.13.17's `parseBody({ dot: true })` drops it; a trailing `x.__proto__` and a top-level `__proto__` are own data keys of a null-prototype group, as are `constructor` and `prototype` (B30 [#410](https://github.com/Laratypes/Laratype/issues/410)). A dot key of more than 33 segments, or a conversion that would create more than 10,000 nested groups, is the malformed-form 400, as Hono 4.13.17's `handleParsingNestedValues` refuses it. A `__proto__` key in a JSON body or query string is an own data key on the object the pipeline builds, never a prototype; a contract's schema drops it like any key it does not declare. A multipart file field is the standard web `File`, so contracts stay browser-safe.
- **Malformed bodies** are a **400**, on 0.5 and `Route.api` routes alike, never a 500: JSON as `{ message: "Malformed JSON in request body." }`; a form body `parseBody()` rejects (a missing or bad multipart boundary, a truncated part) as `{ message: "Malformed form data in request body." }`; a `Content-Type` with more than one media type (a comma outside a quoted-string, RFC 9110 §5.6.4) as `{ message: "Invalid Content-Type header: more than one media type." }`, before the default cap and the parse; a `Content-Type` with a form media type name outside the leading media type (a parameter, an embedded or suffixed leading type, or both names) as `{ message: "Invalid Content-Type header: a form media type name outside the leading media type." }`, before the default cap and the parse. A read of the body stream that fails is that same 400 for its media type, whatever the request's signal says: `@hono/node-server` aborts it on close, but a truncated body can arrive without one, and it is never logged at error level. A body over the [default body limit](./http.md#default-body-limit) (JSON or form 1 MiB, multipart 10 MiB) is the same **413**: the pipeline counts the raw bytes at the start of its read, before parsing. A form body an earlier middleware read with `c.req.formData()` is not counted, because its bytes are already spent; one it parsed with `c.req.parseBody()` is counted on 4.13.17, which caches the body's bytes next to its FormData (see the cached-bodies invariant in [http.md › Default body limit](./http.md#default-body-limit)). Hono's `bodyLimit` keeps its own **413** too: on 4.9.6 it errors the stream with a `BodyLimitError`, which the pipeline rethrows untouched; 4.13.17 buffers the body and answers its 413 before the pipeline runs. A body an earlier middleware took off the raw stream itself is not covered by the default, which cannot rebuild it; that middleware mounts its own `bodyLimit` before reading. A body an earlier middleware read through Hono's readers is served from Hono's cache, and the route's own status still applies: its `c.req.parseBody()` or `validator('form')` FormData, its `c.req.formData()`, its `c.req.arrayBuffer()` bytes, its `c.req.blob()`, or its `c.req.text()` (a urlencoded body is text by definition, so its text is its body). The pipeline converts the cached FormData with its own options, so a flat `c.req.parseBody()` does not hide dot keys, and writes that FormData back to Hono's cache (it is parsed with the request's Content-Type, which a multipart boundary needs), clearing the earlier parse's fields, so a later `c.req.parseBody()` or `c.req.formData()` in route middleware or a 0.5 controller reads it — except on Hono 4.12.28, whose `c.req.parseBody()` re-reads a FormData-only cache as bytes with a new boundary, so it rejects and leaves its failed promise in the cache (`c.req.formData()` reads the FormData until that call; a cache that holds the request's bytes is fine; 4.13.17 converts the cached FormData instead). A `c.req.parseBody()` on a JSON request never reads the stream (4.9.6 cached that `{}`; 4.13.17 caches nothing), so the JSON body is read off `c.req.raw`, and the bytes replace any `{}` a 4.9.6 middleware left, so a later `c.req.text()`/`json()` reads them. The one reader a multipart body cannot be rebuilt from is `c.req.text()`: it keeps characters, not the bytes of a file part, so that state is the generic 500, with its own message — unless the text is blank: an empty or whitespace-only body is no body, `{}`, as for every form body. A body read off `c.req.raw` directly, which leaves the cache empty (`raw.bodyUsed`), is that 500 too, a server bug. Form and JSON follow the same rules. An empty (or whitespace-only) body is no body, `{}` for the JSON and the form types alike, so a client that sends its `Content-Type` on a GET or a DELETE with no body still gets through: the form path reads the body's bytes to tell blank ones from a body (`formData()` rejects an empty multipart body). A form parse an earlier middleware swallowed with its own catch does not change that: a request with no body is still `{}`, including one whose stream is spent (`Content-Length: 0`, what `@hono/node-server` sends for an empty body). A spent stream with no `Content-Length` — an in-process `Request` with `body: ""` — cannot be told from a truncated one, so it is that 400; Hono 4.12.28+ (4.13.17 included) caches its zero bytes, which say blank.
- **Query:** a key sent once is a string, a repeated key an array (how `buildUrl` sends an array). A single value for an array schema (`?tag=a` for `z.array(z.string())`) is a string, so such a schema accepts both (`z.union` or a preprocess). Converting a value is the schema's job: `z.coerce.number<number>()` (zod 4) turns `"2"` into `2`, and defaults apply. The query string is parsed once per request (H31 [#308](https://github.com/Laratypes/Laratype/issues/308)): the contract input and the 0.5 `input()` share it, `input()` keeping the first value of a repeated key as `HonoRequest.query()` did. An array schema on request input should set `.max()` before any `.refine()` or other check: a repeated query key has no length limit of its own, so without it the client chooses how many items the schema walks, and zod 4 only rejects the size before walking the items when the size checks come first (with `.refine()` before `.max()`, every item is validated before the limit rejects).
- **Params** are the raw path params (strings), folder params included. Converting them is `r.bind()` (H7 [#118](https://github.com/Laratypes/Laratype/issues/118)).
- **Validation:** the endpoint's `query` and `body` schemas go through the contract's `validate()` (C3), in that order, after middleware and policies and before the handler. The body itself is read at the start of `RequestKernel.handle`, before the route middleware, so a middleware that needs the raw stream must run before the kernel (`app.use()`). A contract route takes no 0.5 request class: `RequestKernel.handle` with both an `endpoint` and a `request` throws (see Diagnostics).
- **422:** invalid input in the query, the body or both answers **422** with the catalog `errors.validation` body and its code, `{ code: "VALIDATION_ERROR", message: "The given data was invalid.", errors: ErrorBag }`, one bag for both slots (dot paths, unprefixed). Until H5 [#108](https://github.com/Laratypes/Laratype/issues/108) maps a thrown `ContractError`, it is sent as a Hono `HTTPException`, so middleware headers stay.
- **422 messages:** each issue becomes `{ path, message }` only, never the library's `input`, `received` or `keys`, on 0.5 request classes too. The submitted data is the raw request input at the issue's path — the query or the body slot the contract validated, the `all()` object for a 0.5 request class — read from own data properties only: `Object.getOwnPropertyDescriptor` is used and only its `value` read, so a getter is never invoked, the prototype chain is never followed (`__proto__`, `constructor` and `prototype` are never resolved), and an array is walked by index. A printable value there is searched in the message, for every issue code except `invalid_type` (a type name, not the data), case-folded, and for a string in its trimmed form too (a `trim()` transform makes a translated message quote the trimmed value); a default message that ends with the word `received` (in any case) and the value (in any case; valibot `... but received "x"` and `Invalid email: Received "x"`) loses that tail with the separators before it (`, `, `: `, ` but `, and `but` after any separator, as in `Expected x,but`); `received` inside a word (`unreceived`) is not that tail, though the value it carries is still scanned for. The trimmed prefix is scanned again, and a message that still carries the value anywhere — a translated default such as zod-i18n's `Ungültiger Enum-Wert. Erwartet 'a' | 'b', erhalten 'secret'`, or a custom one — is replaced by `Invalid value` (H31 [#308](https://github.com/Laratypes/Laratype/issues/308)); a value the message does not carry (an app's own message, a translated one that dropped it) leaves the message as written. A value shorter than 3 characters is not searched (the exact `received` tail is still cut): a 1-2 character value leaks next to nothing, and searching it would turn the common "too short" messages generic. An object or array at the path is searched through its printable leaves, read under the same rules and bounded at 3 levels and 50 leaves: it answers `Invalid value` only when a leaf of 3 or more characters is in the message or the bound is hit, so an object-level message (`Passwords do not match`) survives. A path that does not resolve falls back to the library's printable `received` (zod 3, valibot); with neither, the message is kept, so a missing value (a required-key issue) never turns generic. zod 4's unrecognized keys after the first `": "` are cut (`Unrecognized key: "a"` → `Unrecognized key`). A cut that leaves nothing, empty or whitespace only (`Received "x"`, `: a`, `" : a"`), becomes `Invalid value`; a message no cut shortened is kept as the app wrote it, an empty one included. A zod `invalid_type` keeps its message. zod 4's regex failures say `Invalid string: must match pattern <regex>` (zod 3 said `Invalid`): the pattern is schema text, not user input, and a custom message hides it.
- **Only invalid input is a 422:** an error thrown inside a schema rejects and ends as the generic 500 ([http.md › Exceptions](./http.md#exceptions)).
- **Context:** the handler context is built from the validated **output** types (`InferOut`), so handlers see coerced and defaulted values.

### Diagnostics
Runtime, besides the 400 and 422 bodies above: a malformed body is that 400 for JSON and form alike, and so is a body read that fails, whether it rejects or throws before returning a promise (a client abort or a truncated stream, no error-level log); a `Content-Type` with more than one media type is the **400** `{ message: "Invalid Content-Type header: more than one media type." }` at the start of the read, before the [default body limit](./http.md#default-body-limit) counts anything; it runs on every request `RequestKernel.handle` serves, before middleware and the handler, so it also applies to a GET with no body and to a route whose endpoint declares no body schema, and repeated `Content-Type` header lines (joined by `Headers.get` with `, `) and an empty element (a leading or trailing comma) are the same 400; a `Content-Type` with a form media type name outside its leading media type (in a parameter, a suffix, or a second name) is the **400** `{ message: "Invalid Content-Type header: a form media type name outside the leading media type." }`, before the default body limit, because Bun's form parser picks the type by a substring search over the whole header while the pipeline reads only the leading type; a body over the [default body limit](./http.md#default-body-limit) or over a `bodyLimit` mounted with `app.use()` before the kernel keeps that **413** (the default counts the raw bytes first; the pipeline rethrows `bodyLimit`'s `BodyLimitError` untouched); a body an earlier middleware read off `c.req.raw` directly, with nothing in Hono's cache, ends as the generic **500** (`{ message: "Server Error" }`, logged with `the request body was already read, so the pipeline cannot parse it`), never as a 400, while one it read through `c.req.parseBody()`, `validator('form')`, `c.req.arrayBuffer()`, `c.req.blob()` or `c.req.text()` is served from that cache (the route's own status still applies) — except a multipart body read with `c.req.text()`, whose file parts cannot be rebuilt, which is the **500**, logged with `a middleware read the multipart body with c.req.text(), so its file parts cannot be rebuilt` (a blank body is `{}` first, never that 500). The generic 500 is also where a `TypeError` from the pipeline's own conversion of a FormData it holds ends: that is a bug, never the malformed-body 400. `RequestKernel.handle` throws a `TypeError` when a contract route also gets a request class, ``<route name or path>: a contract route validates its endpoint's query and body schemas, so it takes no request class (<Request>)``. The route proof reports a handler whose `query` or `body` type doesn't match the schema output as a TypeScript error whose property name is ``<c>.<e>: `query` of the ctx does not match the handler (it is the output of the endpoint's query schema) ``, and the same with `body`, with the detail `{ route_provides, handler_requires }` ([http.md › Route proof at r.contract()](./http.md#route-proof-at-rcontract)).

### Non-goals
- No coercion by the framework: a query value stays a string until the schema converts it.
- No prefix in the error bag for the query or the body.
- The ctx has no headers or request helpers: a handler that needs them reads them from the keys a typed middleware adds ([http.md › Typed middleware](./http.md#typed-middleware), H6 [#117](https://github.com/Laratypes/Laratype/issues/117)), or the 0.5 request with `ContextApi.getRequest()` (`@laratype/support`). Changes 0.5 middleware makes to `input()` don't reach the ctx, which is built from the parsed request.

## FormRequest v2

### Status
planned → [#137](https://github.com/Laratypes/Laratype/issues/137) (H10, M3).

### Design (non-binding)
- **Base class (#137):** `FormRequest<typeof users.store>`, with `messages()`. Message keys are inferred from the schema.
- **No `authorize()`:** a 403 only comes from the `authorize` capability and its policy ([http.md › Authorization from the contract](./http.md#authorization-from-the-contract)).
- **Async rules:** for example a unique email, run as async refinements.
- **i18n:** messages through `@laratype/i18n` ([#167](https://github.com/Laratypes/Laratype/issues/167)).
- **Rules:** the rules default to the contract's body schema. FormRequest only **adds** messages and async rules, and never redefines the schema.
- **Pipeline position:** it runs with validation, after the policies (see [http.md › Request pipeline](./http.md#request-pipeline)).
